# 사람 평가 계획과 개발용 정적 검사 집계

## 1. 검증할 주장

“짧아졌다”, “선호도가 높다”, “문제 없이 실행됐다”, “의미가 보존됐다”는 서로 다른 주장이다. 별도 결과로 보고한다. 이 문서의 표본 수·조건·중단 기준은 **프로젝트 제안**이며 문헌에서 확정한 최적값이 아니다.

목표는 단순한 간결화 지시보다 중요한 의미 손실을 줄이면서 독자의 이해를 돕는지 확인하는 것이다. 실험이 끝나기 전 성능 향상 비율·정확도·오류 감소 효과를 게시하지 않는다.

## 2. 평가를 4개 층으로 나눈다

| 층 | 측정 | 단독으로 말할 수 없는 것 |
|---|---|---|
| 패키지 품질 | 파일·규칙 ID·참조·생성물·자료 형식 | 언어 규칙이 효과적이다 |
| 회귀 사례 | 알려진 위험 사례에서 동작·판정 | 새로운 실무 문서에서 정확하다 |
| 의미 보존 | 독립 검토자의 주장 대응과 오류 판정 | 실제 독자가 더 잘 이해한다 |
| 독자 과제 | 조건 질문 정답률·실행 정확도·소요 시간 | 모든 분야·독자에 효과가 있다 |

## 3. 1차 파일럿 제안

초기 제안은 개발 자료 60개와 잠금 평가 자료 60개다. 각각 API 설명·장애 분석·운영 절차·보안 정책 등 4개 범주에 15개씩 배분한다. 같은 원문에서 만든 변형, 같은 제품·주제의 유사 문단은 반드시 같은 분할에 둔다.

이 120개는 확정 표본 수나 통계적 검정력 보장이 아니다. 파일럿에서 사건율·분산·평가자 일치도를 파악하고 확인 실험의 표본 수를 별도로 정한다.

이번 패키지의 `eval/seed-cases.jsonl`은 새로 작성한 가상 개발용 사례다. 독립 평가 자료가 아니며 공개된 순간 잠금 평가로 사용할 수 없다. 같은 pair_id의 사례를 학습/개발과 시험에 나누지 않는다. AI 작성 기대 라벨은 사람이 검토하기 전 확정 gold가 아니다.

허용 자료: 소유자가 공개를 허용한 글, 사용 조건이 확인된 공개 자료, 독립 작성 가상 자료. 사내 코드·로그·설계서·사용자 실제 대화는 넣지 않는다. 비공개 평가가 필요하면 공개 도구와 데이터를 분리하고 로컬에서만 실행한다.

## 4. 비교 조건

| 조건 | 지시 |
|---|---|
| A: 원문 기준선 | 원문을 수정하지 않음 |
| B: 일반 간결화 | “기술적 의미를 유지하면서 짧고 명확한 한국어로 고쳐라.” |
| C: DOT-STK100 | 같은 원문·독자 조건에 규격과 스킬 적용 |

선택적 후속 비교: C에서 의미 대응 검토를 제거하거나, 길이 15/20어절 경고를 켜거나, 용어집을 제외한다. 한 번에 여러 요소를 바꾸지 않는다. 요약을 요청하는 지시와 의미 보존 교정을 비교하지 않는다.

같은 모델·버전·도구 권한·온도·생성 상한을 사용한다. YSK 규칙의 추가 입력 토큰은 숨기지 않고 비용으로 기록한다. 짧은 출력을 만들기 위해 한 조건만 출력 상한을 낮추지 않는다.

모델 변동 확인이 필요하면 B/C 각 문서에서 3회 반복을 제안한다. 반복 출력은 독립 원문 표본으로 세지 않는다. 모델·프롬프트 수정 이후 잠금 자료로 반복 튜닝하지 않는다.

## 5. 의미 보존 주석

독립 검토자 2명이 조건 이름과 모델 이름을 가린 상태에서 원문-출력을 비교한다. 불일치는 제3 검토자가 판정한다. 이 역할 수는 초기 운영안이다.

각 편집에 원문 구절, 수정문 구절, 영향을 받는 주장, 규칙 ID, 판정과 근거를 남긴다. `compatible`, `meaning_changed`, `needs_context`를 구분한다. 모호한 원문을 임의로 하나의 해석으로 고친 출력은 안전한 교정으로 세지 않는다.

핵심 오류 유형은 조건 이탈, 주체 추가/교체, 부정/수량 변화, 값/단위/경계 변화, 논리/순서 변화, 가능성/의무 변화, 예외 삭제, 근거 없는 사실 추가다. 한국어 구체적 유형은 평가자 간 합의를 확인한 뒤 확정한다.

보고 지표:

- 문서별 중대한 의미 오류 비율: 중대한 오류가 1개 이상인 출력 / 전체 출력.
- 주장별 손실률: 누락·변경된 원문 주장 / 검토 대상 원문 주장. 새 사실 추가는 별도 집계한다.
- `needs_context` 비율과 적절한 보류 비율: 단순 보류 증가로 오류가 감소한 것처럼 보이지 않게 한다.
- 검사기 오탐·미탐: 사람이 확정한 위반/비위반과 비교한 precision·recall, 경고 수/1,000어절.
- 평가자 일치: 원시 일치율, 혼동 행렬, 합의 전·후 건수. 가능하면 Cohen κ 등도 보조 보고하되 희귀 사건 영향을 함께 설명한다.

일반 문체 경고와 의미 오류를 하나의 가중 합계 점수로 합치지 않는다.

## 6. 독자 이해도 과제

문서별로 조건·예외·주체·다음 조치에 관한 객관적인 질문을 2~4개 작성한다. 문체 선호 질문과 분리한다. 정답은 원문과 승인된 근거로 미리 고정한다.

같은 참가자가 같은 원문의 A/B/C를 모두 보지 않도록 배정한다. 조건과 문서 범주를 균형화하고 순서를 무작위화한다. 읽기 전에 대상 분야 경험을 기록한다. 경험을 사후에 유리한 그룹으로 바꿔 분석하지 않는다.

정답률, 실패한 조치 선택, 읽기·답변 시간, 확신도와 선호도를 별도로 기록한다. 실제로 위험한 명령은 실행시키지 않고 모의 환경이나 선택 과제로 평가한다. 빠르게 읽었지만 틀린 경우를 개선으로 처리하지 않는다.

## 7. 통계와 해석

원문·주제 계열을 주요 통계 단위로 쓴다. 같은 원문의 반복 생성·여러 질문·여러 편집을 모두 독립 표본으로 계산하지 않는다. 비교는 원문별로 짝을 맞추고 신뢰구간은 원문 계열 단위의 재표집 등 설계에 맞춰 계산한다. 사람 과제는 참가자 효과도 고려한다.

중대한 오류가 0개여도 실제 오류율 0을 증명하지 않는다. 독립 베르누이 시행이라는 단순 가정에서 n회 중 0건일 때 95% 단측 상한은 `1 - 0.05**(1/n)`이다. n=300이면 약 0.994%다. 서로 연관된 300개 편집을 독립 300개로 대입하면 안 된다. 이 수치는 계산 예시이며 실험 결과가 아니다.

평균 개선만 보고하지 않는다. 중대한 조건 손실 사례·도메인별 역효과·미확인·실패 출력을 포함한다. 잠금 자료에 대한 한 번의 결과와 개발 자료 결과를 분리한다.

## 8. 공개 단계별 게이트

**설계 초안 공개**: 구조 검사 통과, 라이선스·저작자·데이터 공개 승인, 효과 미검증 표시, 알려진 문제 공개가 필요하다. 사람 대상 실험을 안 했어도 초안 공개는 가능하다.

**도구 베타 공개**: 보고 전용, 부작용/외부 통신 없음 확인, 회귀 사례와 실제 호스트 테스트, 지원 범위 명시가 필요하다. seed 사례 성공률을 일반 정확도로 광고하지 않는다.

**v1.0 제안**: 잠금 평가와 독립 검토 완료, 심각한 알려진 미해결 결함 없음, 실제 독자 지표 보고, 실패·보류율 공개, 검토 및 버전 정책 안정화를 요구한다. 통계적 목표와 비열등성 한계는 결과를 보기 전에 소유자가 승인한다. 검증 결과 없이 임의로 “95% 합격” 같은 기준을 정하지 않는다.

## 9. 재현 기록

규격/스킬/용어집 해시, 모델·호스트 버전, 프롬프트, 샘플링 설정, 입력 계열 ID, 생성 시각, 원문 공개 권리, 평가자·합의 절차, 원본 출력, 제외 이유, 분석 스크립트 버전을 남긴다. 개인정보와 비밀을 공개 기록에 넣지 않는다.

`eval/annotation-template.json`은 주석 한 건의 작성 예다. 실제 값이 없는 항목에 0이나 성공을 넣지 않는다. 사람 주석과 독자 실험의 상태는 **미실행**이다. 개발용 정적 검사 집계는 이와 별도로 수행한다.

## 10. 실행한 개발 집계와 사람 검토 대기

`scripts/evaluate_linter.py`는 공개 가능한 합성 56건/28계열에 대해 any-warning 발생 여부를 AI 초안 기대 라벨과 대조한다. compatible을 음성, meaning_changed를 양성으로 두고 needs_context는 이진 지표의 분모에서 제외하며 건수를 따로 기록한다. 경고의 종류가 실제 변경과 관련 없어도 양성으로 세므로 의미 검사 성능이 아니다.

TP/FP/TN/FN, precision, recall, FPR/미탐률과 사례 ID를 보고한다. 분모가 0이면 null이다. 사람 기준 precision/recall은 null로 남긴다. 기대 라벨을 작성·수정한 도구와 같은 작업에서 수행한 개발 집계이므로 독립성도 없다. 같은 계열의 후보를 독립 표본으로 추정하는 신뢰구간이나 일반 성능 수치는 제공하지 않는다.

`eval/human-review-queue.jsonl`은 기대 라벨을 제외한 입력 쌍과 해시, 미기록 검토자/판정 필드를 가진다. 검토자는 서로의 판정을 보기 전에 독립 작성한다. 두 명의 verdict와 주장 구절, 경고별 관련성을 기록한 뒤 불일치는 제3자가 합의한다. 공개 seed 정답을 보지 않도록 안내하되 이 자료가 비공개 잠금 평가라는 주장은 하지 않는다.

사람 기준 오탐은 관련 위반이 없는 위치의 경고, 미탐은 사람이 확인한 위반 중 대응 경고가 없는 항목으로 정의한다. 문서별 경고 여부와 경고별 정확도를 따로 계산한다. needs_context는 보류로 보고하고 경고 수/1,000어절은 공백 기준 어절 계수와 보호 구간 포함 여부를 미리 정한다. 주석 완료 전 사람 지표를 계산하지 않는다.

## 11. 용어 구분 개선의 독립 효과 평가

[용어집](../references/terminology.json)의 48개 예시는 16개 용어 계열의 공개 개발 자료다. 각 계열의 올바른 편집, 의미 변경 반례와 문맥 부족 예시를 함께 검토한다. `./target/release/dot-stk100 evaluate --terminology-examples`는 Linter의 경고 발생만 집계하며, 스킬이 만들어 낸 글의 의미 보존 효과를 측정하지 않는다.

효과 실험은 다음 조건을 갖춘 뒤 실행한다.

1. 비교 조건을 고정한다. 같은 모델, 호스트, 입력, 생성 설정에서 개선 전 스킬과 개선 후 스킬을 별도 문맥으로 실행한다. 두 변형의 결과를 같은 원문 계열로 묶고 무작위 순서의 익명 식별자로 제시한다.
2. 공개 개발 예시와 다른 평가 자료를 독립 작성한다. 정책상 허용된 가상 자료와 공개 권리 자료를 사용하고, 프로젝트별 용어 정의, 인용, 실제 비교 연산이 아닌 이상, 근거가 없는 지원과 호환 주장을 포함한다. 같은 계열은 분할 사이에 나누지 않는다.
3. 독립 검토자 두 명이 어느 변형인지와 AI 기대 라벨을 보지 않고 주장, 상태, 경계, 의무와 증거 범위의 보존 여부를 판정한다. 보류와 불일치를 별도로 남기고 제3자가 합의한다.
4. 독립 검토자가 확정한 의미 변경 문서 비율을 주 지표로 보고한다. 변형별 보류율, 새 사실 추가, 경계값과 의무 수준 오류, 이해 질문 정답률, 소요 시간과 토큰도 분리한다. 원문 계열을 단위로 불확실성을 보고한다.
5. 필요한 표본 수, 중단 조건과 판단 기준은 결과를 보기 전에 정한다. 이 파일럿만으로 일반 개선 효과를 선언하지 않는다. 설정, 입력과 출력 해시, 평가자, 원래 판정과 합의 기록을 보존한다.

현재 독립 사람 주석과 이 효과 실험은 미실행이다. 후보 스킬의 예시 실행이나 구조 검사로 대체하지 않는다.

## 12. 권장 표현의 평가

[권장 표현 사전](../references/preferred-expressions.json)의 24개 합성 예시는 적용 가능한 편집, 의미 변경 반례와 문맥 부족을 구분하는 개발 자료다. 사전과 스킬의 변경 전후를 같은 원문과 생성 설정으로 실행하고, 표현의 직접성뿐 아니라 전문 용어, 부정, 의무, 동작의 시작과 완료가 보존됐는지 독립 검토한다.

익숙한 표현의 선호도와 의미 보존을 별도 지표로 기록한다. Linter의 표현 후보가 늘거나 사라진 것, 예시를 짧게 편집한 것만으로 효과를 입증하지 않는다. 실제 이해도와 오류 감소율은 독립 사람 평가 전까지 미확인으로 남긴다.
