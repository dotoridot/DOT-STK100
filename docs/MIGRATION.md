# STK-100 v0.1에서 DOT-STK100 v0.2로

v0.1은 기본 개념을 정리한 47개 규칙의 초안이었다. v0.2는 이름만 바꾼 버전이 아니라 적용 강도·모드·검토 범위를 다시 설계한 32개 규칙 초안이다. 줄어든 수가 품질 향상을 증명하지는 않는다.

| v0.1 문제 또는 항목 | v0.2 처리 |
|---|---|
| ASD-STK100이라는 개발 가칭 | 공개 이름 DOT-STK100, 독립 규격 고지 |
| 정확성 > 의미 보존의 모호한 순위 | rewrite와 verify를 분리. 사실 수정은 표시·승인 |
| W01–W07 어휘 규칙 | K05–K07, M05와 용어집으로 재구성 |
| S01 한 문장 한 주장 MUST | K01 SHOULD. 분할보다 의미 보존 우선 |
| S02/S09 주체 명시 | K02/K03. 알려지지 않은 주체 추가 금지 |
| S03 조건 우선 | K04 권장 + M02 조건 적용 범위 필수 |
| S04–S05 부정·값 | M03–M04 |
| S06–S08 피동·길이·문단 | K07–K08. 고정 길이 기본 비활성화 |
| P01–P07 절차 | P01–P05. 원문에 없는 복구 행동 추가 금지 |
| D01–D05 설명 | P04, E02/E05, M08 |
| E01–E07 근거 | E01–E05, M07–M08. 문서와 실행의 증거 구분 |
| T01–T07 기술 충실도 | M01–M08, E03 |
| F01–F05 구성 | K06, P04–P05. 획일적 목차 완화 |
| 예시 D에서 SDK 주체 추가 및 뒤 문장의 조건 약화 | 명시적 주체가 있는 독립 가상 예제로 교체. 상위 조건 아래 목록 |
| 초안 프롬프트의 의미 100% 보존 목표 | 목표는 유지하되 보장 문구 금지. needs_context 판정 |
| 근거 없이 점수로 합격하지 않음 | Q02–Q03과 의미/가독성 분리 평가로 구체화 |
| 포괄적인 기관 홈페이지 참고 링크 | 확인한 문서·논문·검토 범위 기록 |

이 표는 범주별 이관표다. 일대일 규칙 동등성을 선언하지 않는다. 이전 문서에 STK-W01 등의 ID가 있으면 새 검토를 거쳐 새 ID를 부여한다. v0.1 원본은 제공된 파일에 남기며, 허가되지 않은 타 자료를 아카이브에 묶지 않는다.

## 0.2.0-draft.3에서 0.2.0-draft.4로

규칙 ID와 강도, 32개 규칙 수는 유지한다. K07과 P04의 문체 기본값을 보완했다. 새 설명과 말투 변경이 승인된 본문에 적용하며 기존 인용, FAQ와 에이전트용 작업 지시문을 일괄 변환하지 않는다. 문체 후보를 자동 위반으로 판정하는 Linter 검사는 추가하지 않았다.

## 0.2.0-draft.4에서 0.0.2로

현재 버전 표기를 정식 0.0.2로 변경했다. 이전 초안 번호와 새 버전은 숫자 크기순으로 비교하는 승격 관계가 아니며 사용자가 선택한 새 버전 체계다. 규칙 32개, ID, 강도, 문체 기준과 실행 코드는 그대로다. 정식 표기는 효과 검증이나 인증 완료를 뜻하지 않는다.

## 미출시 용어집 구조 0.2

배포 버전은 0.0.2를 유지한다. 용어집의 `schema_version`은 0.2이며 기존 TERM-01부터 TERM-12의 ID와 `term_a`, `term_b` 및 정의를 유지하고 4개 쌍과 `rule_ids`, `examples`, `exceptions`를 추가했다. 사전을 확장할 때는 세 종류의 합성 예시와 예외, 유효한 규칙 ID가 필요하다. 과거의 정의와 자동 치환 금지 계약은 유지한다. 의미 구분 경고의 message에는 TERM ID가 추가되므로 메시지 문자열을 파싱하는 소비자는 ID를 참고하되 의미 판정으로 취급하지 않는다.

## 미출시 권장 표현 사전과 Linter 출력 0.2

의미 구분 사전의 구조 0.2는 유지하고, 별도 preferred-expressions.json 구조 0.1을 추가했다. K07의 표현 선택을 구체화하며 규칙 수 32개와 배포 버전 0.0.2는 유지한다. Linter 도구 버전은 0.2.0, 출력 schema_version은 0.2로 바뀐다. expressions 설정 해시가 추가되므로 출력 스키마를 엄격하게 검증하는 소비자는 새 스키마를 사용해야 한다. 기존 check 종류는 유지하며 표현 후보를 terminology/YSK-K07/EXPR ID로 구분한다. 기본 seed와 용어 예시 any-warning 집계에는 문체 후보가 포함될 수 있어 과거 집계와 구분한다.

## Python 스크립트에서 Rust 실행 파일로

규칙 배포 버전 0.0.2와 Linter 출력 schema_version0.2, tool_version0.2.0은 유지한다. CLI 기본 경로는 `dot-stk100 lint/evaluate/render/validate`다. 기존 Python 경로와 확인한 import API는 native 어댑터로 남긴다. 각 호스트에서 release 빌드를 명시적으로 만들며 일반 실행 중 빌드나 다운로드는 없다.

평가기 CLI에는 `evaluation_schema_version: "0.2"`와 `implementation_kind: "rust_executable_sha256"`를 추가한다. `implementation_sha256`은 현재 실행 중인 Rust 바이너리의 bytes 해시이며 과거 Python 소스 해시와 같다고 비교하지 않는다. Python `evaluate(cases)` import API의 집계 결과에는 CLI 전용 식별 필드를 추가하지 않는다.

잘못된 `expected_review`가 배열이나 객체인 두 API 입력은 Python의 unhashable TypeError 대신 `invalid expected_review` 진단을 반환한다. 여전히 유효한 라벨로 허용하지 않으며 비교 도구에 명시적인 차이로 기록한다. Rust parser/OS 오류 문구는 Python과 다를 수 있지만 실패 종료 코드, 빈 stdout, stderr 진단과 입력 bytes 보존을 검사한다.

패키지 재귀 검사에서는 루트의 `.git`, `target`, `bin` 디렉토리를 제외한다. 소스, 규칙과 문서 검사 범위는 유지한다. 비표준 JSON의 NaN/Infinity와 임의 Python 정규식 전체 지원을 보장하지 않는다. 자세한 절차는 [Rust 전환 안내](RUST-MIGRATION.md)를 따른다.
