# 기술적으로 구별할 용어

이 사전은 기술적 의미가 다른 표현을 구별하기 위한 검토 자료다. 한국어 전체의 허용 어휘나 금지어를 정하지 않는다. 정본은 [terminology.json](terminology.json)이며, 기존 12개 쌍을 유지하고 지원, 호환, 동작 확인, 비교 경계와 의무 수준을 포함해 16개 쌍을 관리한다.

## 검토 절차

1. 입력에서 해당 표현이 가리키는 행동, 상태, 비교 기준과 근거를 확인한다.
2. 정본의 관련 항목만 읽고 `id`, `rule_ids`, 두 정의, `examples`, `exceptions`를 대조한다. 예시는 올바른 편집, 의미 변경 반례, 문맥 부족의 세 종류다.
3. 프로젝트의 명시적 정의, UI 표기, 코드와 인용을 우선한다. 다른 정의가 있으면 적용 범위와 이유를 기록한다.
4. 원문과 수정문의 뜻이 같은지 확인한다. 근거가 부족하면 표현을 추측해 채우지 않고 `needs_context`로 남긴다.
5. review에서는 용어 ID, 규칙 ID, 원문과 수정문 구절, 근거 상태와 제안을 보고한다. 예외는 현재 판단에 필요한 경우에만 설명하며, 사전의 예외를 수신자의 새 행동 의무로 추가하지 않는다. rewrite에서는 확인된 의미를 유지한다.

## 주요 구분

| 항목 | 구분 | 확인할 내용 |
|---|---|---|
| TERM-01 | 탐지 / 차단 | 발견 또는 판정과 실제 행위 제한 |
| TERM-02 | 미수행 / 실패 | 작업 실행 여부와 성공 조건 |
| TERM-13, TERM-14 | 지원 / 호환 / 동작 확인 | 제공자의 지원 범위, 함께 사용할 수 있다는 주장, 특정 시험에서 관찰한 결과 |
| TERM-15 | 이상 / 초과 | 비교 기준값 포함 여부 |
| TERM-16 | 권장 / 필수 | 권고와 의무의 차이 |

예를 들어 검사를 실행하지 않았다는 원문을 검사에 실패했다고 바꾸면 실행 상태가 달라진다. 한 환경에서 동작을 확인한 결과를 모든 지원 환경의 호환 보장으로 확대해서도 안 된다. 반대로 제품이 실행 전 오류를 실패 코드로 정의했다면 코드 이름은 유지하고 실제 실행 여부를 따로 설명한다.

`이상`은 비정상 상태라는 뜻으로도 쓰인다. 단어가 보인다는 이유만으로 수치 비교 위반을 확정하지 않는다. 지원과 호환도 분야마다 정의가 다르므로 정본 정의를 모든 제품의 사실처럼 적용하지 않는다.

## 도구와 평가의 경계

Linter는 용어 사용량이 교차해 변한 경우 `TERM-*` ID를 포함한 경고 후보를 보고한다. 문장의 의미나 단어 간 대응을 확정하지 않는다. 단어 개수가 같게 남은 역할 교환은 놓칠 수 있고, 서로 다른 문장에서 정상적으로 추가하거나 삭제한 표현도 경고할 수 있다. 프로젝트 예외를 자동 해석하거나 자동 치환하지 않는다.

각 항목의 예시 3개, 총 48개는 공개 개발용 합성 자료이며 AI 초안 기대 라벨이다. 독립 사람이 합의한 정답이나 잠금 평가 자료가 아니다. [평가 계획](../docs/EVALUATION.md)에 따라 규칙이 실제 오류를 줄이는지는 별도로 측정해야 한다.
