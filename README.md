# DOT-STK100

**DOT Simplified Technical Korean — 사람이 사람에게 기술 내용을 명확하게 설명하기 위한 한국어 작성 규격.**

ASD-STE100의 접근을 한국어에 응용했습니다. 독자가 조건과 행동을 이해하고, 작성자가 기술적 의미를 보존하며 설명을 다듬도록 돕는 것을 목표로 합니다.

저작자: **dotoridot** · 기획·프로젝트 관리: **dotoridot** · 버전: `0.0.2` · 상태: 정식 버전, 효과 검증 전

## 만든 이유

영어에는 기술 문서를 단순하고 명확하게 쓰기 위한 [ASD-STE100(Simplified Technical English)](https://www.asd-ste100.org/about.html)이 있습니다. 작성 규칙과 통제 어휘를 바탕으로, 독자가 기술 문서를 이해하도록 돕는 접근입니다.

이 프로젝트의 계기 중 하나는 [안드레이 카파시(Andrej Karpathy)가 공유한 활용법](https://x.com/karpathy/status/2105819303471976479)입니다. 그는 LLM에 ASD-STE100 방식으로 설명을 요청하면 더 읽기 쉬운 답변을 얻는 데 도움이 됐다고 소개했습니다. 이 사례를 보고, **“이런 접근을 한국어 기술 설명에도 적용할 수 없을까?”**라는 생각을 했습니다.

이 아이디어를 한국어 기술 문서와 사람 사이의 설명에도 활용하고 싶었습니다. 동료에게 기능을 설명하고, 사용자에게 장애 상황을 알리고, 새 팀원에게 절차를 안내할 때 적용할 수 있는 일관된 기준이 필요했습니다. DOT-STK100은 그 아이디어를 한국어의 표현과 문장 구조에 맞게 응용한 프로젝트입니다.

한국어에서는 생략된 주체, 조사의 차이, 부정과 조건의 범위가 뜻을 바꿀 수 있습니다. 따라서 영어 규칙을 그대로 옮기기보다, **기술적 의미를 유지하면서 읽기 쉽게 설명하는 것**을 목표로 삼았습니다. 문장을 짧게 만드는 것보다 **조건·부정·수치·주체·예외·근거 수준을 보존하는 것**을 우선합니다.

SDK/API 문서, 코드 리뷰, 장애 안내, 운영 절차를 작성하거나 다듬을 때 사용합니다.

이 프로젝트는 ASD·STEMG와 관계없는 독립 프로젝트입니다. 공식 한국어판·공인 표준·인증 도구가 아닙니다. `100`은 이름의 일부이며 규칙 수나 품질 점수가 아닙니다.

## 주요 독자와 사용 상황

- 개발자: 동료에게 기능과 API 동작을 설명할 때
- 운영·지원 담당자: 사용자에게 장애 상황과 확인된 사실을 알릴 때
- 업무 담당자: 새 팀원에게 작업 조건과 절차를 안내할 때

## 작성할 때 지킬 원칙

1. **독자와 목적을 정합니다.** 독자가 이미 아는 내용과 설명을 읽고 이해하거나 실행해야 할 일을 확인합니다.
2. **핵심을 먼저 설명합니다.** 설명은 핵심 내용부터, 작업 안내는 사전 조건부터 제시합니다.
3. **조건과 예외를 행동 가까이에 둡니다.** 어떤 경우에 무엇을 해야 하는지 함께 읽을 수 있게 씁니다.
4. **독자에게 필요한 용어를 설명합니다.** 낯선 용어는 짧게 정의하고 같은 개념에는 같은 용어를 씁니다.
5. **의미를 유지하며 다듬습니다.** 문장을 나누거나 표현을 줄여도 수치·부정·주체·예외·불확실성을 유지합니다. 원문에 없는 정보는 추측해서 채우지 않습니다.

## 기술적으로 구별할 용어

같은 개념에는 같은 용어를 쓰고, 서로 다른 행동과 상태는 구별합니다. 한국어 전체의 표현을 제한하는 대신 기술적으로 혼동하면 안 되는 16개 용어 쌍을 관리합니다. 각 항목에는 용어 ID, 관련 규칙 ID, 정의, 올바른 예시, 잘못된 예시, 문맥이 필요한 예시와 예외가 있습니다.

| 구분 | 확인할 차이 |
|---|---|
| 탐지 / 차단 | 발견과 실제 행위 제한 |
| 미수행 / 실패 | 작업 실행 여부 |
| 지원 / 호환 / 동작 확인 | 지원 범위와 특정 환경에서 관찰한 결과 |
| 이상 / 초과 | 비교 기준값 포함 여부 |
| 권장 / 필수 | 권고와 의무 |

[용어 구분 절차](references/TERMINOLOGY.md)와 [용어집](references/terminology.json)의 정의는 문맥을 확인하기 위한 기준입니다. 프로젝트 정의, UI 표기와 인용을 우선하며 자동 치환하지 않습니다. 근거가 부족하면 판단을 보류합니다.

ASD-STE100의 용어 관리 원칙을 선택적으로 참고하지만, 영어 승인어를 번역하거나 공식 한국어판을 제공하는 것은 아닙니다. [공식 자료 확인과 적용 범위](references/STE-COMPARISON.md)에 근거를 정리했습니다. 이 개선이 의미 변경 오류를 줄이는지는 독립 효과 평가로 확인해야 합니다. 현재 검사 범위와 남은 한계는 [용어 구분 검증 기록](reports/TERMINOLOGY-VALIDATION.md)에 정리했습니다.

## 제목과 본문의 문체

제목은 문서의 내용을 바로 알 수 있는 짧은 명사구로 씁니다. 본문은 작성자가 동료에게 사실, 이유와 조건을 설명하는 말투를 기본으로 합니다. 작성 과정과 적용 규칙은 검토 기록에 남기고, 독자에게 전달할 본문에는 필요한 내용을 담습니다.

절차에서는 독자가 해야 할 행동을 안내합니다. FAQ, 인터뷰와 요청된 대화체는 질문형을 유지할 수 있습니다. 원문의 말투와 인용은 보존하며, 말투 변경을 요청받은 경우에만 그 범위에서 바꿉니다. 사람의 경험이나 실행 이력을 근거 없이 추가하지 않습니다.

## 적용 전후 예시

아래는 사람이 다른 사람에게 설명하는 세 가지 상황입니다. 예시는 이 프로젝트를 위해 작성한 가상 자료이며, 실제 제품 사양이나 효과 검증 결과가 아닙니다. 각 예시의 수치와 조건은 설명 전에 주어진 정보입니다.

### 1. 개발자가 동료에게 API 동작을 설명할 때

동료가 재시도 조건과 예외를 이해하도록 설명합니다.

**설명 전**

> 서버 응답을 5초 이내에 받지 못한 경우 클라이언트는 요청을 최대 3회 재시도하도록 되어 있으나, 사용자가 취소한 요청에 대해서는 재시도가 수행되지 않습니다.

**설명 후**

> 서버 응답을 5초 이내에 받지 못하면 클라이언트는 요청을 최대 3회 재시도합니다. 단, 사용자가 취소한 요청은 재시도하지 않습니다.

재시도 조건, 최대 횟수, 취소 예외를 찾기 쉽게 나눕니다. 대기 시간과 횟수는 원문 그대로 유지합니다.

### 2. 운영 담당자가 사용자에게 장애 상황을 알릴 때

사용자가 현재 겪을 수 있는 문제와 조사 상태를 이해하도록 안내합니다.

**설명 전**

> 현재 일부 사용자의 로그인 실패 현상이 확인되고 있으며, 네트워크 지연과의 연관성이 있을 가능성에 대한 조사가 진행 중이나 원인이 확정된 상태는 아닙니다.

**설명 후**

> 현재 일부 사용자가 로그인하지 못하고 있습니다. 네트워크 지연과 관련이 있는지 조사하고 있습니다. 원인은 아직 확정되지 않았습니다.

사용자에게 발생한 문제를 먼저 알리고 조사 상태를 이어 설명합니다. 일부 사용자의 문제를 전체 장애로 확대하거나, 조사 중인 내용을 확정된 원인으로 바꾸지 않습니다.

### 3. 담당자가 새 팀원에게 작업 절차를 안내할 때

새 팀원이 작업을 시작할 조건과 중단해야 할 상황을 알도록 안내합니다.

**설명 전**

> 백업이 완료된 것을 확인한 후 설정 파일을 변경하고 서비스를 재시작해야 하며, 백업에 실패한 경우에는 설정 변경을 진행하지 말고 담당자에게 알려야 합니다.

**설명 후**

> 백업 완료를 확인한 뒤 다음 순서로 작업하세요.
>
> 1. 설정 파일을 변경하세요.
> 2. 서비스를 재시작하세요.
>
> 백업에 실패하면 설정을 변경하지 말고 담당자에게 알리세요.

시작 조건과 작업 순서를 분리하고, 백업 실패 시의 행동을 명시합니다. 원문에 주어진 순서와 중단 조건을 유지합니다.

추가 사례와 잘못된 단순화는 [교정 예시와 반례](examples/BEFORE-AFTER.md)에서 확인할 수 있습니다.

## 문서 작성 절차

설치 없이 [규격](references/DOT-STK100-SPEC.md)과 [사례](examples/BEFORE-AFTER.md)를 읽고 문서에 적용할 수 있습니다.

1. 설명할 독자와 목적, 확인된 자료를 정합니다.
2. 전달할 핵심 내용과 조건·수치·예외를 적습니다.
3. 독자가 필요한 정보를 찾기 쉬운 순서로 배치합니다.
4. 문장을 다듬은 뒤 원문과 비교해 빠진 정보나 새로 추가한 주장이 없는지 확인합니다.

동료와 검토할 때도 같은 기준으로 확인할 수 있습니다. 정적 검사 도구와 AI는 이 과정을 보조하는 수단으로 사용할 수 있습니다.

## 제공되는 것과 제공되지 않는 것

제공: 규격, Lite/Core/Audit 스킬 경로, 용어 구분 사전, 합성 회귀 사례, 로컬 보고 전용 Linter, 오탐/미탐 집계 도구, 사람 검토 대기 자료, 패키지 구조 검사기.

미제공: 의미 동치 증명기, 학습 모델, 사람 대상 효과 검증, 실제 호스트별 설치 테스트.

## AI 보조 도구로 사용하기

문서 초안 작성과 교정을 AI에 맡길 때는 아래 프롬프트나 스킬을 사용할 수 있습니다. 작성자는 결과를 원문과 대조하고, 독자에게 전달할 내용을 검토합니다.

### 바로 사용할 프롬프트

```text
첨부한 DOT-STK100 규격과 SKILL.md를 읽고 rewrite 모드로 편집하세요.
이 글은 [작성자 역할]이 [독자]에게 [설명 목적]을 전달하는 문서입니다.
기술적 주장·조건·부정·수치·단위·식별자·예외·불확실성을 보존하세요.
원문의 오류나 모호성은 별도로 표시하고, 사실을 몰래 바꾸지 마세요.
문장 길이 때문에 정보를 삭제하지 마세요. 원문에 없는 주체도 추가하지 마세요.
결과는 수정문, 중요한 변경, 확인 필요 사항으로 나누어 제시하세요.
```

프로젝트 이름만 쓰면 모델이 규칙을 알고 있다고 보장할 수 없습니다. 규격을 함께 제공하거나 실제로 읽을 수 있는 스킬로 설치해야 합니다.

### 스킬 설치와 사용

공개 저장소는 [dotoridot/DOT-STK100](https://github.com/dotoridot/DOT-STK100)입니다. 설치 위치는 아래와 같습니다. 기존 동명 폴더가 있으면 덮어쓰기 전에 변경 내용을 비교해야 합니다.

| 호스트 | 프로젝트 설치 | 개인 설치 |
|---|---|---|
| Codex | `.agents/skills/dot-stk100/` | `~/.agents/skills/dot-stk100/` |
| Claude Code | `.claude/skills/dot-stk100/` | `~/.claude/skills/dot-stk100/` |

다음은 프로젝트 범위에서 Git으로 설치하는 예시입니다. 두 명령은 사용할 호스트에 따라 선택합니다. Git 설치본에는 업데이트를 위한 `.git`이 포함됩니다.

```bash
# Codex 프로젝트 설치
git clone https://github.com/dotoridot/DOT-STK100.git .agents/skills/dot-stk100

# Claude Code 프로젝트 설치
git clone https://github.com/dotoridot/DOT-STK100.git .claude/skills/dot-stk100
```

다운로드한 패키지를 복사하는 경우에는 캐시, `.git`, `private`, `local-runs`를 제외한 전체 폴더가 필요합니다. `SKILL.md`만 복사하면 참조가 깨집니다. 설치한 스킬은 Codex에서 `$dot-stk100`, Claude Code에서 `/dot-stk100`으로 호출합니다. 경로와 형식은 공식 문서에서 확인했지만 실제 두 호스트의 모델 실행은 미검증입니다. [설치 근거와 시험 상태](docs/HOST-COMPATIBILITY.md)를 참고하세요.

프로필은 검토 깊이입니다. Lite는 짧은 설명, Core는 문서 작성과 교정, Audit은 의미 변경 위험 검토에 사용합니다. 모드는 작업 종류입니다. `explain`은 설명, `rewrite`는 표현 교정, `review`는 검토, `verify`는 사실 확인입니다.

```text
$dot-stk100 Lite explain: 요청 타임아웃과 사용자의 취소는 어떻게 다른가요?
```

## 보고 전용 Linter

```bash
python3 scripts/lint_text.py --source examples/source.md --candidate examples/candidate.md --format json
python3 scripts/evaluate_linter.py --terminology-examples
```

결과는 수정 없이 stdout JSON으로 보고합니다. 모든 경고는 후보입니다. 종료 코드 0이나 경고 없음은 의미 보존 합격이 아닙니다. [검출 범위, 위치 규약, 오탐과 미탐](docs/LINTER.md)을 확인하세요.

## 로컬 구조 검사

Python 3.11 이상을 이 패키지의 지원 목표로 정했습니다. 런타임 외 추가 의존성·네트워크 연결은 필요하지 않습니다.

```bash
python scripts/render_rules.py --check
python scripts/validate_package.py
python -m unittest discover -s tests -v
python scripts/evaluate_linter.py
```

이 명령은 파일 구조·참조·테스트 자료 형식을 검사합니다. 문장의 의미와 사실을 검증하는 명령이 아닙니다. 실행 기록은 [검사 보고서](reports/VALIDATION.md)에 있습니다.

## 저작자와 라이선스

인용 이름은 **dotoridot**입니다. [AUTHORS.md](AUTHORS.md)와 [CITATION.cff](CITATION.cff)에 프로젝트 저작자 표기를 준비했습니다.

문서, 규칙, Skill, 합성 자료, 실행 코드와 테스트를 모두 [MIT 라이선스](LICENSE)로 제공합니다. 저작권 고지의 저작자는 dotoridot입니다. 외부 표준과 논문 등 제3자 자료의 권리는 각 권리자에게 있으며 원문을 묶어 배포하지 않습니다.
